How caching actually works across one RSC request

Two separate caching layers are involved, with two very different lifetimes. Mixing them up is the usual source of confusion.

1. Apollo's cache — lives for one request, then is thrown away

sequenceDiagram
    participant U1 as Request #1
    participant A1 as ApolloClient
(fresh cache)
    participant SC1 as ServerComponent A
    participant SC2 as ServerComponent B
    participant API as GraphQL API

    U1->>A1: registerApolloClient() factory runs
    SC1->>A1: query(GetContinents)
    A1->>API: fetch (cache miss)
    API-->>A1: data
    A1-->>SC1: data
    SC2->>A1: query(GetContinents) — same request
    A1-->>SC2: data (from this request's cache, no 2nd fetch)
    Note over A1: request finishes → client + cache discarded

    participant U2 as Request #2 (new user, or same user again)
    participant A2 as ApolloClient
(fresh cache)
    U2->>A2: registerApolloClient() factory runs again
    Note over A2: no memory of Request #1 at all
What this buys you Two server components asking for the same data in the same page render share one network call. That's the entire job of this cache — deduplication within a request, not storage across requests.

2. The actual cross-request cache sits one layer lower

graph TD
    SC["Server Component
calls query()"] --> AC["Apollo Client
(per-request cache)"]
    AC --> HL["HttpLink
→ calls fetch()"]
    HL --> FC{{"Next.js fetch cache
keyed by URL + options
survives across requests"}}
    FC -->|cache hit, within revalidate window| AC
    FC -->|cache miss / expired| API[("GraphQL API")]
    API --> FC
Why not share Apollo's cache instead It has no concept of "which user." A persistent in-memory Apollo cache on the server would leak one user's response into another user's request. Next's fetch cache is safe to share because it's keyed purely by URL/args, never by who asked.

Where this repo's code sits today

createHttpLink(uri) in packages/apollo-client/src/links/http-link.ts doesn't set fetchOptions.next.revalidate yet — so that bottom layer in diagram 2 is currently disabled. Every RSC query is a live network call, every time.

Passing { fetchOptions: { next: { revalidate: 60 } } } on the HttpLink turns it back on.

Request flow: nam-web

Two request shapes through the same AWS footprint: a page load (synchronous, round-trip) and a mutation that fans out into an async job (generate or execute a workflow). The orange boxes are the two places this architecture deliberately pays for a warm instance instead of scaling to zero, because cold starts there would delay the thing the user is staring at.

Figure 1 page load / GraphQL query

Every request — HTML page, RSC payload, or a GraphQL query made from inside a React Server Component — takes this same path. Static _next/static/* assets branch off at CloudFront and never reach the origin on a cache hit.

  1. 1Browser → CloudFront — single HTTPS request for the page, an RSC payload, or (on a client-side mutation) a GraphQL call made from the browser itself.
  2. 2CloudFront branches on path: _next/static/* is served straight from S3 (no origin hit on a cache hit, 1-year TTL since filenames are content-hashed); everything else forwards to the ALB.
  3. 3ALB — reachable only from CloudFront's managed prefix list, forwards to the Fargate task on port 3000.
  4. 4ECS Fargate runs the Next.js standalone server. React Server Components render here; if the page needs data, the server itself calls the GraphQL API over HTTPS.Kept at min 1 task on purpose — no scale-out cold start, deterministic render latency.
  5. 5API Gateway (HTTP API) — the GraphQL endpoint's public front door, proxies straight through to Lambda.
  6. 6The integration targets the live alias of the api Lambda, not $LATEST.That alias carries Provisioned Concurrency (1 unit) — RSC renders hit this Lambda on every page load, so it's warmed the same way the web server is.
  7. 7api Lambda reads/writes DynamoDB (workflows, executions tables) to resolve the query.
  8. 8Response (GraphQL JSON) flows back through API Gateway → Fargate, where it's folded into the rendered HTML/RSC payload → ALB → CloudFront → browser.

Figure 2 mutation → async job → live push

"Generate workflow" and "Execute workflow" don't wait for the real work — step 6 above enqueues a job and returns immediately. The job runs on a separate Lambda, and its result reaches the browser over a WebSocket connection the page already opened on load, not as an HTTP response.

One connection the diagrams can't show as a hop: on page load, the browser also opens a persistent WebSocket straight to AppSync Events' realtime endpoint and subscribes to this workflow's channel. Figure 2's last arrow lands on that existing connection — it's not a new request.
